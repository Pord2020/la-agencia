# Sprints y entregas (modo consultora)

El usuario **no pulsa un botón opaco**. Cada sprint se comporta como el de una empresa de TI.

## Ciclo

1. **Planificación** — el PO explica: “Para planificar usaremos un modelo más capaz (cuesta más tokens) y sacaremos el plan antes.”
2. **Wireframes e informes** — pantallas, flujos y diagramas en lenguaje llano.
3. **Aprobación del usuario** — “¿Vamos con este plan?”
4. **Ejecución** — especialistas + coding adapter; la oficina muestra quién trabaja.
5. **Entrega del sprint** — capturas, checklist, URL de prueba.
6. **Feedback** — “Trabajamos en X. ¿Qué opinas? ¿Vamos bien?”
7. **Ajustes** — change requests en lenguaje de negocio → nueva tarea, no rehacer el universo.

## Artefactos obligatorios por sprint (MVP)

| Artefacto | Descripción |
|-----------|-------------|
| Resumen ejecutivo | 5–10 líneas: qué se hizo y por qué |
| Wireframes / bocetos | Antes o durante, según el sprint |
| Diagrama de flujo | Cómo se conectan las partes |
| Capturas o preview | Prueba real en la web |
| Checklist de aceptación | Sí / No / Comentar |
| Coste estimado | Tokens/tiempo de cuota usados (si se conoce) |

## Transparencia

Durante la ejecución, la UI muestra estados legibles:

- “El Líder Técnico está ordenando el backlog…”
- “Frontend implementando el botón de pagos (oficina Cursor)…”
- “QA revisando en el navegador…”
- “Cuota Cursor al 82 % — te avisamos si llega al 90 %.”

## Épicas

Al cerrar una épica: informe más amplio + demo + decisión de continuar o pivotar.
